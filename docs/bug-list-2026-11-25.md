## 一、P1（明显功能错误，建议优先修）

### D1 截图取消/超时后 uTools 主窗口永久隐藏

- **端**：uTools
- **证据**：`src/views/Word/Word.vue:3407-3493`；`src/utils/pic-translate.ts:305-324`；`src/adapters/impl/capture-utools.ts:11-28`
- **现象/原因**：`startScreenCapture` 在 L3414 先 `hideMainWindow()`，`showMainWindow()` 只在成功路径 L3419。截图取消（`capture-utools.ts:19-21` reject「截图取消」）、2 分钟超时、base64 格式异常都会落到 L3483 的 catch，既不恢复窗口也不弹全局提示——错误只写进已隐藏窗口内的 `ocrError` 弹窗。用户表现为「点截图后插件消失且不再出现」。
  另外 `ocrTranslateMultiPlatform` 内部（`pic-translate.ts:305-307`）会再 hide 一次，且只通过 `onCaptured` 回调通知「截图已完成」；`Word.vue:3417` 调用时未传该回调，窗口恢复责任完全落在调用方。
  注 1：`pic-translate.ts:297` 的每日额度检查在 hide **之前**执行，因此额度超限不会触发此问题；真正触发场景是截图取消/超时/数据异常。
  注 2：已查 uTools 官方 API 文档（`https://share121.github.io/codeing/utools/api`）：`screenCapture` 仅负责取图，**不保证**自动恢复窗口，官方示例明确要求「先 `hideMainWindow()` → 回调里 `showMainWindow()`」配对。故本条确认成立；真机上若发现截图取消时系统自行恢复了窗口，则影响降级为「截图超时/接口异常路径」，但代码侧的 hide/show 不配对仍应修复。
- **修复建议**：`startScreenCapture` 用 `try/finally` 包住 `ocrTranslateMultiPlatform`，finally 中统一 `showMainWindow()`（与 `App.vue:520` 的 `restoreUtoolsMainWindow()` 写法一致）；或由 OCR 层在 `finally` 中自行恢复并要求 `onCaptured` 必传。
- **验证**：已复核（含官方文档核对窗口 API 契约）。

### D2 OCR 语言包缓存命中时丢弃新语言数据，非英语本地识别结果错误

- **端**：uTools/Electron/Web（本地 OCR）
- **证据**：`src/utils/pic-translate.ts:1176-1185, 1235-1292`
- **现象/原因**：IndexedDB 缓存只有一个固定 key `worker_bundle`（`CACHE_KEY`），内容含 `{worker, core, lang}`，不区分语言。`getOrCreateWorker` 在语言切换时（L1194）会终止旧 worker 重建，重建流程：
  1. L1245 为非英语下载对应语言包（`jpn/rus/spa/fra`）；
  2. L1260 读缓存，命中则 L1271 直接用 `cached.lang` 作为 `langDataBase64`；
  3. L1279 新下载的数据被丢弃，worker 内按 `lang` 命名写入（如 `jpn.traineddata`）——实际是旧语言（通常是 eng）数据。
  结果：只要缓存已存在，切换到日/俄/西/法词库做本地 OCR，识别结果错乱（用英语模型冒充目标语种）。
- **修复建议**：缓存 key 按语言区分（如 `worker_bundle_${lang}`），或缓存命中时校验缓存语言与当前 `lang` 一致，不一致则走文件/新下载路径。
- **验证**：已复核。

### D5 移动端 `useSignin.todayStr` 无依赖 computed，跨午夜后打卡状态冻结

### D11 服务端推送「未变更跳过」导致 blob 过期后无法自助获取新同步码

- **端**：桌面端（自建连接码同步）
- **证据**：`src/utils/sync-server.ts:427-432, 456`
- **现象/原因**：上传成功后把指纹哈希写入 `localStorage['slowlyrecord-last-push-hash']`，此后数据未变更即跳过上传并返回 `code: ''`；该 key 没有任何清理逻辑。服务端 blob 过期后（下载侧报「同步码无效或数据已过期」），用户再点推送仍被跳过，无法获得新同步码，只能手动清 localStorage 或修改数据。
- **修复建议**：记录哈希时同时记录时间戳，超过服务端 TTL（与 blob 过期策略一致）则不跳过；或在下载失败/明确报过期时清除该 key。
- **验证**：已复核。

### D12 本地文件导出同步数据未脱敏，非商店端含明文 API 密钥（发布阻断）

### D13 商店版备份导入非商店端时密文密钥可能被原样写回

### D15 移动端远程词库缓存按「字符数」分块，多字节词库必超 storage 上限

- **端**：移动端（微信小程序）
- **证据**：`mobile/src/utils/remote-wordbank.ts:16, 181-202`

### D24 OCR Worker 空闲清理定时器不重排，Worker 可能永久驻留

- **端**：桌面端（本地 OCR）
- **证据**：`src/utils/pic-translate.ts:1187-1230, 1323-1334`
- **现象/原因**：`scheduleWorkerCleanup()` 只在**创建** Worker 时调用一次（L1227）。后续使用只更新 `lastUsedTime`（L1202/L1211/L1223），不重排定时器。若创建后 5 分钟内被使用过，定时器触发时判断「未超时」直接结束——既不释放也不重排 → Tesseract Worker 及 WASM 内存常驻不再回收。
- **修复建议**：清理定时器改为循环（未超时则按剩余时间重排），或在每次使用后重排（注意先 clearTimeout 旧定时器）。

### D25 Electron 端 file 适配器在 ESM 产物中 `require` 失败，静默降级

- **端**：Electron
- **证据**：`src/adapters/file.ts:198-206`；`electron/main.cjs:58-63`

- **修复建议**：改为 `await import('./impl/file-electron')` 并把 `getFileAdapter` 改为异步初始化（或预先在应用启动时 `import()` 注入），与 `getCaptureAdapterAsync` 同模式。
- **验证**：已复核（nodeIntegration 配置确认）。

### D26 批量加词与 setTimeout 异步调用为 fire-and-forget
