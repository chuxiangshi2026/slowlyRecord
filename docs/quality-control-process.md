# 质量把控流程

> 状态：项目质量管控基线，后续列入开发者必读文档。
>
> 建立日期：2026-11-25
>
> 适用范围：`src/`、`mobile/src/`、`electron/`、`public/`、构建配置、脚本及随代码变更的数据生成链路。
>
> 配套文档：[代码规范](./coding-standard.md)、[代码审查标准](./code-review-standard.md)、[黑盒 E2E 测试与 uTools 实机巡检规范](./blackbox-e2e-testing.md)、[仓库工作指南](../AGENTS.md)。

## 1. 目标与原则

本流程用于降低功能缺陷、跨端回归、数据丢失、安全泄露和发布事故，不以流程文档代替实际验证。

- **验收先于实现**：先明确预期行为、异常行为和验收方法，再修改代码。
- **变更最小化**：一次变更解决一个明确问题，不夹带无关重构、格式化或依赖升级。
- **审查与实现分离**：即使只有一名开发者，也必须经过一次独立的 diff 自审；高风险变更再增加一轮脱离实现思路的复审。
- **以证据为准**：命令结果、测试用例、真实操作和审查记录是完成依据，不能以“应该没问题”代替。
- **真实产物验证**：类型检查和单元测试不能替代构建产物上的端到端验证。
- **失败不隐藏**：不重试到偶然通过、不删除失败用例、不缩小验证范围后宣称全部通过。

代码审查和测试只能降低风险，不能承诺发现所有 bug；必须通过分层检查和发布后反馈持续收敛。

## 2. 单人项目中的职责

开发者同时承担实现、审查、验证和发布职责，但各阶段必须分开执行：

1. **实现者**：说明需求、影响范围、风险与回滚方式，完成代码和必要测试。
2. **审查者**：离开实现思路，依据《代码审查标准》重新阅读完整 diff 及受影响调用链，记录发现和未覆盖项。
3. **验证者**：在最终代码和真实构建产物上执行验收，不以开发早期的结果替代最终结果。
4. **发布者**：确认所有发布门禁通过、无未接受的阻断问题，并保留可追溯结果。

可以使用 AI 辅助审查，但 AI 的结论必须经代码位置、复现步骤或测试核实；AI 输出本身不是通过证据，也不能替代发布责任。项目提供 [`code-quality-review`](../.agents/skills/code-quality-review/SKILL.md) 技能，用于按本流程执行变更审查、发布检查和全库审计；使用该技能仍须遵守相同的证据与门禁要求。

本文中的“必须”为质量门禁，“应该”为无合理理由不得省略的要求，“可以”为可选项。

## 3. 变更风险分级

开始实现前确定最高适用等级；无法判断时按较高一级处理。

| 等级 | 典型变更 | 最低控制要求 |
| --- | --- | --- |
| 低风险 | 纯文档、注释、文案，且不改变运行行为 | 核对内容与链接；检查 diff，无夹带代码或生成物 |
| 中风险 | 局部 bug 修复、普通 UI 交互、单模块功能 | 完整自审；全量测试和桌面类型检查；受影响场景实测；必要构建 |
| 高风险 | 数据结构与迁移、同步/备份、复习算法、鉴权与密钥、共享 adapter/store/util、窗口生命周期、构建配置、依赖升级、跨端公共逻辑 | 在中风险基础上增加受影响端构建与 E2E、回归测试、异常/兼容性验证、第二轮独立复审和明确回滚方案 |

以下情况必须升为高风险：修改公共数据契约、删除或批量改写数据、影响多个平台、改变持久化格式、触及商店合规、无法轻易回滚。

## 4. 标准流程

### 4.1 变更前：定义问题与边界

必须完成：

- 写清目标、非目标、验收标准和受影响平台。
- bug 修复先记录实际结果、预期结果和最小复现步骤；找到根因及所有受影响调用方后再修复。尚未确认的部分明确标为假设。
- 用 `git status --short` 确认工作区已有改动，避免混入他人或未完成任务。
- 梳理影响链路：入口 → 调用方 → 状态 → 持久化/外部服务 → UI → 构建产物。
- 确认是否涉及旧数据兼容、迁移、同步冲突、回滚和商店版本差异。
- 高风险变更先确定验证数据和回滚方案；可能损伤用户数据时，先准备可恢复的测试备份。

### 4.2 实现中：控制改动与回归面

- 新代码和本次修改的逻辑必须遵守《代码规范》；历史格式问题不得混入功能变更统一重排。
- 沿用项目现有架构、命名、平台适配层和工具函数，不绕过 adapter 直接调用平台 API。
- 优先修改共同根因位置，避免只在某一个调用方修补症状。
- bug 修复和非平凡逻辑必须留下能防止复发的自动化测试；测试应覆盖正常、边界和失败路径。
- 不新增非必要依赖、抽象或配置，不做与本次目标无关的清理。
- 修改生成数据的源文件后，必须运行项目规定的生成脚本；生成文件不得手工改写。
- 修改 `AGENTS.md` 已描述的行为、结构或命令时，同步更新对应说明。

### 4.3 提交前：独立代码审查

至少完成一轮最终 diff 审查：

```bash
git status --short
git diff --stat
git diff
git diff --cached
```

- 按《代码审查标准》检查正确性、异常路径、数据兼容、安全、跨端行为、性能和测试有效性。
- 不仅阅读改过的行，还要阅读相关函数上下文、全部调用方和关键被调用方。
- 发现问题后修复，并对修复内容及受影响部分重新审查。
- 高风险变更进行第二轮复审；可以换一个干净上下文或使用 AI 辅助，但必须独立核实结论。
- 审查记录必须列出未验证项，不能只写“看过”或“LGTM”。

### 4.4 自动化验证：执行真实门禁

所有代码变更在提交前至少运行：

```bash
npm run test:run
npm run type-check
```

`npm run test:run` 已包含 `src/**` 与 `mobile/src/**` 的 Vitest 用例。修改移动端应用或移动端测试时，还必须运行：

```bash
npm run type-check:mobile
npm --prefix mobile run type-check:test
```

根据影响范围运行构建：

```bash
npm run build             # uTools：类型检查 + 构建
npm run build:web         # Web + SEO 页面与产物处理
npm run build:electron    # Electron
npm run build:mp-weixin   # 微信小程序
```

针对构建产物运行黑盒 E2E：

```bash
node scripts/e2e/blackbox.cjs --dist dist
node scripts/e2e/blackbox.cjs --dist dist-web
node scripts/e2e/blackbox.cjs --dist dist-electron
```

缺少浏览器时，先按《黑盒 E2E 测试与 uTools 实机巡检规范》准备环境，不得用跳过 E2E 代替环境修复。

专项要求：

| 变更范围 | 额外必须执行/检查 |
| --- | --- |
| `src/App.vue` 入口、`src/utils/pic-translate.ts`、`public/plugin.json` features | `npx vitest run src/app-enter.test.ts`，并逐项执行仓库的 uTools 链路自查清单 |
| UI、路由、抽屉、弹窗 | 受影响产物的黑盒 E2E；人工检查加载、空态、错误态和关键交互 |
| 数据、同步、备份、复习调度 | 旧数据兼容、失败恢复、重复执行、边界时间和回归测试；必要时做迁移与回滚演练 |
| 商店提交 | 使用 `npm run build:store`，不得用普通 `build` 替代；核对密钥、同步负载、剥离脚本和合规门禁 |
| 发布 | CI 全部通过；四端构建、三端 E2E、受影响平台实机巡检及发版检查全部完成 |

开发期间可以运行单文件测试快速反馈，但最终必须用规定范围的全量命令复核。`npm run test:coverage` 可用于发现测试盲区，但覆盖率数字不能代替有效断言，当前不虚构覆盖率达标线。

### 4.5 场景验证：走通用户真实链路

必须在最终交付物上验证原始场景，不能只确认 import、编译或用例通过。

至少覆盖：

- 主成功路径，以及与本次改动相关的返回、取消、重试和再次进入。
- 空输入、空结果、非法输入、重复操作、快速连续操作和较长数据。
- 网络/系统/第三方调用失败、超时和不可用时的可见反馈与资源恢复。
- 旧版本数据、首次启动和已有用户状态。
- 改动涉及的平台差异；模拟器无法覆盖的窗口、热键、OCR、截屏、小程序原生能力必须实机验证。

每项结果应能对应验收标准。无法执行的项目必须写明原因、影响和替代验证，不能默认视为通过。

### 4.6 提交与 CI

- 提交前再次检查 `git status --short` 和最终 diff，只提交本任务需要的源文件、测试和文档。
- 不提交临时日志、截图、调试代码、测试输出或本地配置；不手改 `dist/`、`dist-electron/`、`release/` 等产物。
- 遵守仓库提交规范，包括提交时间与批次间隔要求。
- PR 或推送到 `master` 后确认 CI 的 `quality` 和 `builds` 均通过；CI 失败时以最终提交为准修复并重新验证。
- 对看似与本次无关的失败，先确认是否基线已有并保留证据。不得把红项写成通过，也不得顺手修复无关问题扩大变更。

### 4.7 发布与发布后

发布前必须冻结明确的提交版本，并确认：

- 所有必跑命令在最终代码上通过，CI 为绿色。
- 严重及以上审查发现均已关闭；一般问题已修复或明确记录、评估并被接受。
- 发布包来自规定构建命令，尤其是商店包必须走 `build:store`。
- 数据迁移、备份恢复和回滚路径已按风险验证。
- 已知限制、未完成验证和用户可见变化有明确记录。

发布后出现缺陷时，先控制影响并保留现场，再走根因分析、最小修复、回归测试和审查流程。若同类缺陷重复出现，必须检查测试盲区和审查清单，而不是只修当前实例。

## 5. 完成定义（Definition of Done）

一个变更只有同时满足以下条件才可称为完成：

- [ ] 需求或 bug 的验收标准已满足，原始场景在最终交付物上走通。
- [ ] 变更范围最小，无无关文件、临时产物、调试代码或真实密钥。
- [ ] 已完成代码审查，发现的问题有处理结论，高风险变更已完成第二轮复审。
- [ ] 必要的新增/更新测试有效，规定范围内的测试、类型检查、构建和 E2E 均通过。
- [ ] 正常、异常、空态、边界、旧数据和受影响平台已按风险验证。
- [ ] 相关文档、注释、生成数据和 `AGENTS.md` 说明已同步。
- [ ] CI 通过；所有未验证项和剩余风险已明确记录，没有被静默当成通过。

## 6. 失败、受阻与紧急修复

- **测试失败**：先定位原因；不得通过删除、跳过或放宽断言来消除失败。偶发失败按缺陷处理，记录 flaky 用例并修复根因。
- **环境受阻**：优先修复标准命令的运行环境。仍无法执行时，明确列出未跑项和受阻原因，由发布者决定是否接受风险，不能宣称完整验证。
- **范围无法完整交付**：先完成未受阻部分并说明缺口，不得自行缩小验收标准后宣布完成。
- **紧急修复**：允许缩小改动，但不能省略复现、最小回归验证、类型检查和发布门禁；下一工作日内补齐完整审查、回归测试和文档。

## 7. 周期性质量活动

- **每次变更**：变更 diff 审查和受影响调用链审查。
- **每次发布**：全量自动门禁、受影响平台真实巡检、未关闭问题复核。
- **每季度或重大版本前**：按《代码审查标准》执行一轮全库审计；重大数据、同步、安全架构调整后必须额外触发。
- **出现重复缺陷或 flaky 测试时**：立即开展专项审计，不以重跑代替处理。

全库审计可以分模块、分多次完成，但必须记录覆盖范围和未覆盖范围；只检查部分模块时，结论只能称为“专项审查”或“抽查”，不能写成“全量审查”。
