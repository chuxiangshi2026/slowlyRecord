# 代码规范

> 状态：项目编码基线，与[质量把控流程](./quality-control-process.md)、[代码审查标准](./code-review-standard.md)配套使用。
>
> 建立日期：2026-11-25
>
> 适用范围：桌面端 `src/`、移动端 `mobile/src/`、Electron/preload、构建与数据脚本、测试和样式。

## 1. 目标与适用原则

本规范用于统一新代码、降低理解和维护成本，并使代码审查有一致依据。重点是好读、正确、可验证，不追求形式上的统一或一次性改造历史代码。

- **新代码必须遵守本规范**；修改旧代码时，本次涉及的新增逻辑必须遵守。
- 仓库存在历史格式差异。修改旧文件时跟随该文件主流风格，不得在功能变更中夹带整文件重排、引号转换或行尾转换。
- 纯格式治理应单独进行、单独审查；未配置统一工具前，不宣称已有自动 lint/format 门禁。
- 平台兼容、数据安全和既有公共契约优先于风格偏好。确需偏离规范时，在代码或审查记录中说明具体原因。
- 优先复用项目已有实现，不为未来需求预设抽象，不为了“统一”重写已稳定工作的模块。

规范中的“必须”是审查门禁，“应该”是无合理理由不得省略的要求，“可以”是可选项。

## 2. 文件格式与基础排版

新建 TypeScript、Vue、JavaScript 和 SCSS 文件默认使用：

- UTF-8 编码、LF 行尾、文件末尾保留一个换行。
- 2 个空格缩进，不使用 Tab。
- TypeScript/JavaScript 使用单引号；Vue/HTML 属性使用双引号；JSON 遵循 JSON 标准。
- 新文件省略非必要分号。旧文件已有明确分号风格时保持一致，避免自动分号插入歧义。
- 不留行尾空白，不连续堆叠空行，不用对齐空格制造易碎排版。
- 长表达式按语义换行，不机械追求固定列数；一行不得承载多个复杂操作。

import 应清晰分组并避免重复：

1. 运行库和第三方依赖；
2. 项目 alias 导入；
3. 相对路径导入；
4. 仅类型导入使用 `type`，可以与值导入并列。

不得保留未使用的 import、变量或调试代码。不要仅为了排序、扩展名或引号偏好修改未涉及代码。

## 3. 命名与文件组织

### 3.1 命名

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 变量、函数、普通属性 | `camelCase`，名称表达业务含义 | `currentWordBank`、`loadReviewWords` |
| 类型、接口、类、组件构造名 | `PascalCase` | `WordBank`、`DbAdapter` |
| 模块级固定键名、不可变配置 | `UPPER_SNAKE_CASE` | `DEFAULT_INTERVALS`、`CURRENT_BANK_KEY` |
| 布尔值 | 使用 `is`、`has`、`can`、`should` 等语义前缀 | `isReview`、`hasPermission` |
| 事件处理函数 | `handle` + 事件/动作 | `handleSubmit`、`handleCancel` |
| 异步加载/保存函数 | 动词开头，名称体现结果 | `loadUserSet`、`saveWordBank` |
| Vue 组件文件 | `PascalCase.vue`；路由约定的 `index.vue` 除外 | `SharePreview.vue` |
| 普通工具、服务文件 | `kebab-case.ts` | `wordbank-manager.ts` |
| store/composable | 导出使用 `useXxx`，文件名与导出对应 | `useWordsStore.ts`、`useTheme.ts` |
| 测试文件 | 与被测文件同目录、同名加 `.test.ts` | `words.test.ts` |
| CSS 类名 | `kebab-case`，体现块或功能 | `review-card`、`task-item` |

- 不使用无含义的 `data`、`temp`、`item2`、`flag` 承担核心逻辑；短作用域中的 `id`、`key`、`index` 可以使用。
- 不在同一概念上混用近义词，例如词库统一使用所在模块已有的 `wordBank`/`bank`，不得新增 `wordLibrary` 等同义字段。
- 缩写沿用项目通用形式，如 `id`、`url`、`ocr`、`tts`；不得创造难懂缩写。
- Pinia store 与 composable 要区分：新 Pinia store 推荐使用 `useXxxStore`，纯组合函数使用 `useXxx`；历史导出不得仅为改名而改名。

### 3.2 文件与依赖方向

- 桌面端平台能力放入 `src/adapters/`，功能数据存取放入对应 `src/utils/*-db.ts`，共享类型放入 `src/types/` 或既有领域类型文件。
- 移动端沿用 `mobile/src/stores/`、`adapters/`、`utils/` 与分包结构，不随意跨主包/分包引用。
- 局部只使用一次的类型、helper 优先留在使用模块；出现真实复用后再提取共享文件。
- 一个文件聚焦一个主要职责。组件过大时按独立交互块、数据流或复用价值拆分，不按固定行数机械拆分。
- 避免循环依赖；不得靠动态 import、重复代码或 `any` 掩盖不合理的依赖方向。
- 桌面端与移动端默认独立演进，只有现有 `@shared/` 等通道明确支持且完成双端验证时才共享代码。
- 生成文件不得手改；修改源数据后执行对应生成脚本，并提交规定的源文件与生成结果。

## 4. TypeScript

### 4.1 类型设计

- 公共函数、跨模块 API、store 状态和持久化文档必须有明确类型；导出函数应显式声明返回类型，局部简单表达式可以依赖类型推断。
- 对象数据结构使用 `interface` 或 `type`，联合值、判别联合和交叉类型使用 `type`；同一模块保持一致。
- 外部输入、OCR/翻译响应、反序列化数据先按不可信数据处理，使用 `unknown`、类型守卫或运行时校验后再进入业务逻辑。
- 新代码不得使用 `any` 逃避类型设计。既有第三方边界确需保留时，应限制在最小范围并说明原因。
- 不得用 `@ts-ignore`、非空断言或强制断言掩盖未处理的空值。确有类型测试或第三方类型错误时，优先 `@ts-expect-error` 并写明原因。
- 不为绕过错误放宽 tsconfig、扩大 `skipLibCheck` 用途或把领域类型改成宽泛 `Record<string, any>`。
- `null` 与 `undefined` 的含义按数据契约统一；持久化前明确它们是否可序列化，不混用表达同一种状态。
- 可选字段表示真实可选，不要把所有字段设为可选来迁就未初始化对象。
- 固定字符串集合优先使用联合类型或既有枚举，避免任意字符串造成静默拼写错误。

### 4.2 实现方式

- 优先使用 `const`；需要重新赋值时才使用 `let`，不使用 `var`。
- 优先使用小型纯函数承载计算，把 IO、平台 API 和用户提示放在明确的边界层。
- 魔法数字、键名和重复分支条件应提取为有业务含义的常量；仅使用一次且语义清晰的字面量不必抽象。
- 不提前返回无意义结果，也不嵌套过深；使用 guard clause 处理非法输入和提前退出。
- 不修改函数输入对象，除非该函数名称和契约明确表示原地修改。共享状态写入必须经过所属 store 或数据模块。
- 复制数据时选择满足需求的最浅方式；只有确实需要隔离嵌套数据时才深拷贝大对象。
- 使用数组索引、对象键和外部枚举前检查边界，不假设返回列表非空或字段一定存在。
- 时间、时区、金额式精度、排序和去重等规则必须明确，不依赖偶然的当前环境。

## 5. Vue 组件与 Pinia

### 5.1 Vue 组件

- 新组件使用 Vue 3 `<script setup lang="ts">` 和组合式 API，不新增 Options API 组件。
- `props`、`emits` 和暴露给父组件的 API 必须有类型；不在子组件中直接修改 props。
- 脚本中使用 `camelCase` props，模板中遵循 Vue 的属性传递约定；`v-model` 使用明确的 `modelValue`/参数和 `update:` 事件。
- 只保存必要源状态，派生值使用 `computed`；不要用 `watch` 同步维护一份本可计算出来的重复状态。
- `watch` 用于副作用，依赖应明确；避免在回调中反复修改其监听源形成循环。
- 模板保持表达性，复杂判断、格式化和数据转换放入 computed 或有名称的函数。
- `v-for` 使用稳定业务 ID 作为 key，不使用会随增删排序变化的数组索引；避免同一节点上混用 `v-if` 与 `v-for`。
- 不使用 `v-html` 渲染用户、网络、OCR 或翻译返回内容；确需富文本时必须使用可信来源和明确清理策略。
- 定时器、事件订阅和异步回调必须考虑组件卸载；在相应生命周期清理，不向已销毁组件写状态。
- 提交、保存和触发外部调用的交互必须处理防重、加载、失败、取消与恢复。
- 复用 Element Plus、UniApp 和项目现有组件，不为单个页面引入新的 UI 体系。

### 5.2 Pinia 与响应式状态

- store 持有共享业务状态和动作，页面私有展开态、输入草稿等不必全局化。
- 状态字段应有单一事实来源；词库、语言、复习状态等共享概念不得在多个 store 各自维护可互相矛盾的副本。
- 修改状态的动作应完成必要的校验、异常处理和持久化，不把半成品状态留给调用方猜测。
- 异步初始化必须可重复调用或明确保证只调用一次；并发加载应复用 Promise 或防止旧结果覆盖新结果。
- 大列表根据实际性能选择 `shallowRef` 等机制，但不得绕过响应式后直接修改又依赖界面自动刷新。
- 持久化恢复必须补齐新增字段并兼容旧数据，不能用新版本默认对象直接覆盖用户已有设置。
- 注意桌面端 Pinia 3.x 与移动端 Pinia 2.x 的版本差异，不复制未经双端验证的用法。

## 6. 异步、错误与资源管理

- 异步函数必须返回可等待的 Promise，调用方必须 `await` 或显式处理；不得留下无意的 floating Promise。
- 主动发起但无需等待的任务必须说明原因，并设置错误处理；不能用空 `.catch(() => {})` 隐藏失败。
- 同一模块保持一种主要错误契约：抛出异常或返回结构化结果。不要让调用方同时猜测异常、空值和布尔值三种失败方式。
- 底层数据/适配器模块返回可诊断错误，上层交互模块决定用户提示；只有当前层能恢复或转换错误时才捕获。
- 错误日志应保留动作、平台、关键 ID 等上下文，但不得输出密钥、完整用户文本或私人数据。
- `try/catch` 只包住需要处理的异步范围；加载态、窗口隐藏、锁和临时资源使用 `try/finally` 配对恢复。
- 截图、OCR、翻译、网络及系统调用必须使用现有超时机制和失败降级；不得假设第三方一定返回。
- 重试必须考虑幂等、次数上限和退避，禁止无限重试；保存、导入和同步重试不得产生重复数据。
- 旧请求可能晚于新请求返回时，使用取消、请求序号或当前状态校验避免覆盖新结果。
- 事件监听、定时器、对象 URL、子窗口和缓存必须有明确所有者与释放路径。

## 7. 数据、同步与安全

- 跨平台数据访问统一经过 `DbAdapter`；非 uTools 环境在同步 `getDbAdapter()` 前必须先 `await getDbAdapterAsync()`。
- 数据库键、文档 ID 前缀和同步字段使用集中常量或既有生成函数，不在页面散落拼接。
- 新增/修改持久化字段时，同时设计默认值、旧数据读取、序列化、迁移、回滚和测试。
- 迁移必须幂等；批量覆盖和删除前验证范围，失败时保留可恢复数据。
- 日期序列化格式遵循所在模型；新共享契约优先使用明确的 epoch 毫秒或 ISO 字符串，不在同一字段混用 `Date`、秒时间戳和字符串。
- 同步与备份必须保持字段白名单、删除标记、冲突处理和版本语义一致，不直接序列化包含密钥或本机引用的完整内存对象。
- 密钥只能经项目规定的安全配置链路处理；不得写入源码、日志、统计、普通导出或测试样本。
- 商店版的加密、本机大体积存储和免费额度限制不得被新代码绕过。
- Electron IPC、preload 和文件操作必须验证来源、参数和路径，不向渲染层暴露不必要的系统能力。
- 不使用真实用户数据做开发调试或测试夹具；测试样本必须脱敏。

## 8. 平台专项约束

### 8.1 桌面端与 uTools

- 共享 `src/` 的修改必须考虑 uTools、Web、Electron，不直接调用 `utools.*`、原生 IndexedDB 或其他单一宿主 API。
- `__PLATFORM__`、`__STORE_BUILD__` 只通过现有构建与平台判断方式使用，不在业务中散落重复的平台判断组合。
- 主窗口隐藏后，成功、失败、取消、空结果和提前返回都必须恢复；优先统一 `try/finally`。
- `action.payload` 按入口类型解释，不把主输入框文本、超级面板内容和系统选中文本混为一谈。
- 新增 action 时检查分派互斥、默认入口、排除清单和对应 fake utools 集成测试。

### 8.2 移动端与小程序

- 微信小程序的数据和重模块使用静态 import，不新增运行时动态 `import()`。
- 分包只能引用允许范围内的模块；桩库等数据副本必须经既有生成脚本同步，不复制出第三份手工数据。
- 新页面根节点挂载 `themeClass`，样式使用 `--sr-*`；需要原生导航栏/tabBar 时同步处理配色。
- 静态资源放入 `mobile/src/static/` 或规定分包 static，不使用 `mobile/static/` 作为小程序资源目录。
- 使用相机、相册、分享、canvas、地图和音频时处理权限拒绝、用户取消、空结果和平台不支持。
- 小程序滚动父链、固定高度、`box-sizing` 等约束按现有页面模式实现，不用桌面浏览器经验推断真机行为。

### 8.3 构建、脚本与生成数据

- 构建脚本保持可重复执行，输入、输出和失败退出码明确；失败时不得继续发布半成品。
- 脚本不得硬编码某台机器的绝对路径、真实凭证或个人目录。
- 修改知识包、诗词、公式、几何图、背景图等源数据后，执行对应转换/渲染脚本和版本更新。
- 不手改 `dist/`、`dist-electron/`、`release/`，也不把本地测试报告当成源代码提交。

## 9. 样式与主题

- 样式使用 SCSS 和项目 CSS 变量；桌面端使用 `--utools-*`、`--el-*`，移动端使用 `--sr-*`。
- 主色、背景、边框、文字和状态色不得写死；语义功能色和项目明确允许的分类配色除外。
- 不引入蓝色系默认主题或高饱和大面积背景，不覆盖项目统一主色变量。
- 新组件样式优先 `scoped`；确需全局或穿透子组件时缩小选择器范围，避免污染其他页面。
- 类名使用 `kebab-case`，优先语义类，不依据 DOM 层级堆砌冗长选择器。
- 不用 `!important` 和不断增加的 `z-index` 解决普通优先级问题；第三方组件覆盖确需使用时说明原因。
- 同时检查亮色、暗色、自定义背景、长文本、滚动和小窗口；移动端检查根节点高度和横向溢出。
- 动画与模糊效果不得破坏文字可读性和主要交互，低性能平台应有克制实现。

## 10. 注释、日志与用户文案

- 源码注释使用中文，解释“为什么”、平台限制、数据兼容和非显而易见的约束，不复述代码表面行为。
- 公共 adapter、复杂数据契约和非平凡算法应有必要 JSDoc；简单 getter 和自解释函数不强制注释。
- 不留注释掉的旧实现、姓名日期式修改记录或无处理条件的空泛 TODO。确需 TODO 时写清触发条件或关联问题。
- 修改行为后同步更新相关注释、用户文档和 `AGENTS.md`，不得保留描述旧逻辑的注释。
- 桌面端日志使用 `src/utils/logger.ts` 的 `log.d/i/w/e`；其他目录沿用现有日志方式，不新增非必要日志库。
- 不在新代码中留下 `console.log` 调试输出；日志内容不得包含密钥、完整用户文本或其他可识别个人信息。
- 用户文案说明发生了什么、是否影响数据以及下一步怎么做；不只显示“失败”“错误码”或技术堆栈。
- 正常取消不等于错误，空结果不等于系统异常，两者不得静默，也不得滥用错误提示。

## 11. 测试代码

- 测试与源码同目录，命名为 `*.test.ts`；使用项目现有 Vitest、Vue Test Utils 和 fake IndexedDB，不引入第二套测试框架。
- bug 修复必须有回归测试，非平凡分支、解析、数据迁移、复习调度和安全路径必须有行为断言。
- 测试名称描述输入与预期行为，不使用“test1”“正常工作”等无信息名称。
- 测试不访问真实网络、生产同步、真实密钥或用户数据库；时间、随机数、系统 API 和外部响应必须可控。
- 每个用例隔离数据库、storage、定时器、mock 和全局状态，不能依赖执行顺序。
- mock 只替代外部边界，不mock掉本次要验证的核心逻辑；禁止为了通过而修改断言或放宽结果。
- 回归用例应能在未修复代码上失败；无法直接验证时记录替代证据。
- 不为追求覆盖率给简单赋值、常量或无分支代码堆无意义用例。

## 12. 依赖、性能与复杂度

- 新依赖必须有现有依赖/标准库无法满足的明确理由，并评估维护状态、体积、平台兼容、许可证和锁文件影响。
- 不为了少数几行逻辑引入完整工具库，也不重复造项目已有的日期、文本、存储或异步工具。
- 先测量再优化；优化记录数据规模、瓶颈和验证结果，不把猜测当性能结论。
- 大列表、批量持久化、图片和同步数据重点检查内存、序列化次数、主线程阻塞和缓存增长。
- 缓存必须有键、生命周期和失效规则；不得用无限增长的全局对象保存所有历史数据。
- 优先直白实现。接口只有一个实现、配置只有一个值、抽象只有一个调用方时，不提前建立额外层次。

## 14. 已知缺陷防复发规则

以下规则来自 2026-11-25 全量静态复查。修改同类代码时必须主动检查，不得等待再次出错后修补。

### 14.1 窗口、事件与异步结果

- 主窗口、加载态和弹窗的隐藏/关闭必须与恢复配对；截图取消、超时、空数据和异常都在 `finally` 恢复，错误提示不得只写入隐藏页面。
- 启动队列、定时器回调、事件回调和批量任务中的 Promise 必须显式接管；`void` 只能用于已有 catch 的调用，不能作为忽略错误的手段。
- 同一 UI 允许新请求覆盖旧请求时，必须使用请求序号、取消或当前输入校验；在途去重不能替代不同请求之间的过期响应保护。
- `touchend` 与 `tap` 等可能连续派发的手势事件只能有一个业务动作入口，或用手势已处理标记去重。
- 所有动画、防抖和延迟回调必须有句柄，并在页面卸载或状态失效时取消；不得让卸载后的回调继续推进业务数据。

### 14.2 时间、统计与搜索

- 不得用无响应式依赖的 `computed(() => new Date())` 表示“今天”。跨天状态必须在 `onShow`、显式刷新或可靠定时器中更新，并用假定时器测试跨午夜。
- 日期状态与记录读取失败要分别处理；读取失败不得设置“永不重试”的加载完成标记。
- 同一页面的总数、今日数、错题数和完成数必须明确属于当前词库还是全部词库，不得无文案说明地混用。
- 搜索 UI 宣称匹配哪些字段，实现和测试就必须覆盖哪些字段；普通文本、通配符、空释义和大小写分支分别验证，防止恒真条件使分支成为死代码。
- “忘记”“答对”“撤销”是否计入目标必须采用统一产品口径，并由测试锁定；同步更新时间不得借用作学习统计时间。

### 14.3 缓存、外部服务与并发资源

- 缓存键必须包含所有会改变内容的维度，例如语言、版本、平台或数据源。切换语言后复用旧语言模型属于错误缓存命中。
- 缓存未变跳过策略必须有与服务端有效期一致的过期恢复路径；远端数据过期后，用户无需清空 storage 或修改数据即可重新上传。
- 外部音源、OCR、翻译等服务必须有与使用地区相匹配的降级或可见失败；不得给非主语言只保留一个已知不可用的服务。
- 音频等可下载资源必须从 URL 稳定推导缓存键，预取和播放共用同一缓存规则，注释不得宣称实际不存在的离线能力。
- 空闲清理定时器在未达到释放条件时必须按剩余时间重排，不能只更新最后使用时间后让一次性定时器自然结束。

### 14.4 存储、分片与备份恢复

- 同步返回 `ok` 不等于真实落盘完成。刷新、关闭、恢复完成和备份成功提示前，必须等待 Promise 写队列或适配器 `whenIdle`。
- 不得为调用 `whenIdle` 新增 `any` 绕过；应通过 adapter 类型、异步 API 或明确的可选能力接口暴露。
- 字符串分块按存储平台要求的 UTF-8 字节数计算，不得用 UTF-16 `string.length` 代替；切片后必须能无损重组，并测试中日韩及代理对字符。
- 分片读取必须核对预期分片数，缺片要有告警和明确降级，不得遇缺号静默截断。写入失败不得留下可被误认为完整的新旧混合版本。
- 大文档不得无上限写入单个 storage key；写失败必须保留脏状态、允许重试并给用户可见提示。
- 恢复、覆盖和批量删除应使用 Map 等索引结构避免不必要的 O(n²)，并验证部分失败、重复执行和旧数据保留。
- 处理不可信备份对象时使用 own-property 判断，禁止 `in` 将 `constructor` 等原型属性误认为有效数据。

### 14.5 密钥与数据通道

- 所有同步、导出和上传通道默认不携带 API/OCR 密钥；新增通道必须复用统一脱敏函数，并测试负载而不是只检查函数名。
- 本地完整备份与同步文件是不同数据通道，不得因“都是导出”而复制密钥策略。
- 密文恢复必须 fail closed：无法解密时明确告警并保留可恢复状态，不得把 `enc:v1:` 当明文发送，也不得静默清空整条密钥。
- 密钥、用户原文和备份内容不得进入日志、统计或错误上报。

### 14.6 领域常量与平台边界

- 复习等级上限、掌握阈值和等级到间隔的映射必须只有一个来源；所有到期、升级、同步和旧数据钳制路径共用，不得分别使用 `MAX_LEVEL` 与 `intervals.length - 1`。
- 到期边界统一 `>=` 或既有明确口径，并测试等级 0、上限、上限外旧数据及恰好到期时刻。
- 小程序分包不得引用其他分包模块；共享能力提升到主包 adapter/util，不能用复制实现制造第二份维护源。
- 渲染进程不得假设 CommonJS `require` 可用；平台实现按既有异步 adapter 初始化模式加载，失败不得静默替换成功语义不同的实现。
- 业务代码使用窗口、剪贴板等 adapter，不在页面重复直接调用 `utools.*`；事件监听使用可移除的具名回调并有明确生命周期。

### 14.7 UI 与验证结论

- 白色文字、进度和按钮必须检查浅色背景可读性，颜色使用主题变量，不用单独页面的暗黑覆盖弥补浅色缺失。
- 进度公式明确当前项是 0 基索引还是 1 基数量，最后一张必须达到 100%；导入成功提示使用实际导入数而非下载原始数。
- 静态审查结论必须区分“代码路径确认”“运行时复现”“产品口径待决定”。未复验的平台问题不得写成“全部成立、无误报”。
- 审查范围必须与实际读取目录一致；只检查 `src/` 和 `mobile/src/` 不得声称覆盖 Electron 主进程、脚本和 CI 的全库审计。
