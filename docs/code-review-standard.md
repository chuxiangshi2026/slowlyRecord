# 代码审查标准

> 状态：项目代码审查基线，与[质量把控流程](./quality-control-process.md)、[代码规范](./coding-standard.md)配套使用。
>
> 建立日期：2026-11-25
>
> 适用对象：人工自审、复审、AI 辅助审查和全库审计。

## 1. 审查目的与边界

代码审查用于系统发现正确性、兼容性、安全性、可维护性和测试缺口，而不是检查个人风格偏好。

本标准支持三种审查：

1. **变更审查**：每次代码变更必须执行，覆盖完整 diff、相关上下文、全部调用方和受影响运行链路。
2. **专项审查**：针对数据同步、安全、性能、某个平台或某类重复缺陷执行。
3. **全库审计**：按第 8 节覆盖全部第一方代码模块，并明确排除项和未验证项。

“全量”指规定范围内的代码和检查项都有记录，不等于保证发现所有 bug。未发现问题的结论必须有审查范围、验证命令和场景证据支持。

## 2. 单人项目的审查要求

- 实现完成后先运行必要测试，再以审查者身份重新阅读代码；不能边写边勾选审查项。
- 审查必须针对最终变更，不得在后续修改后沿用旧结论。
- 高风险变更必须增加第二轮独立复审，优先换一个干净上下文，从需求和失败场景出发寻找反例。
- AI 可以辅助列出假设和可疑点，但每个发现都必须核实真实代码、调用链或复现结果；禁止把模型猜测直接登记为确定缺陷。
- 审查不得只评价风格，也不得因“单人项目”免除记录和验证。

## 3. 问题严重度与处理门禁

| 级别 | 判定标准 | 示例 | 处理要求 |
| --- | --- | --- | --- |
| 阻断（Blocker） | 数据不可恢复损失、真实密钥泄露、严重安全漏洞、构建/测试门禁失败、核心功能完全不可用 | 同步覆盖用户数据、商店包泄露明文密钥、应用无法启动 | 必须立即修复并重新完整验证，禁止提交或发布 |
| 严重（Major） | 常见路径结果错误、明显回归、重要平台功能失效、可复现崩溃、迁移不兼容 | 复习等级计算错误、取消截图后窗口不恢复、旧数据读取失败 | 提交或发布前必须修复并补回归测试 |
| 一般（Minor） | 影响有限的边界问题、可恢复的交互问题、明确的技术债 | 罕见空态显示不完整、非关键重复逻辑 | 原则上修复；延期必须记录影响和理由，不得伪装成已解决 |
| 建议（Nit） | 不影响正确性的可读性或一致性改进 | 命名可更清晰、注释可精简 | 不阻断，但不得借建议夹带大范围修改 |

严重度按实际影响和数据可恢复性判定，不按修复成本判定。无法确定时先按较高级别处理，并补充复现证据。

## 4. 标准审查步骤

### 第一步：固定审查对象

```bash
git status --short
git diff --stat
git diff
git diff --cached
```

- 记录提交号或工作区范围，包含未跟踪但属于本次变更的源文件。
- 区分源码、测试、生成文件、构建产物和本地临时文件。
- 确认没有真实密钥、私有文档内容、调试代码和无关变更。

### 第二步：建立需求与影响映射

- 每个改动能对应一个需求、bug 或必要回归防护。
- 写出被修改行为的前置条件、输入、输出、副作用和失败表现。
- 列出受影响平台、数据版本、用户状态和回滚方式。
- 对 bug 修复核对根因是否位于共同路径，而非只修补报告中的单一入口。

### 第三步：阅读完整上下文和调用链

- 阅读改动所在函数/组件的完整实现，而非只看 diff 行。
- 搜索全部调用方、实现方、事件发送方与接收方，确认契约仍一致。
- 追踪共享 store、adapter、持久化文档、路由参数和异步事件的生命周期。
- 检查是否有其他平台或旧数据路径绕过本次修复。

### 第四步：逐项执行检查清单

只标记实际检查过的项目；不适用项写明“不适用”及原因。发现必须包含位置、证据和影响，格式见第 9 节。

### 第五步：验证并复审

- 对可疑问题优先用最小复现或测试证明，不靠直觉下结论。
- 修复后重新运行相关检查，并复查是否引入新问题。
- 最终结论只能为“通过”“修改后复审”或“不通过”。存在未接受的阻断/严重问题时不得通过。

## 5. 通用代码审查清单

### 5.1 需求与正确性

- [ ] 实现与验收标准一致，没有只做部分路径或改变未要求的行为。
- [ ] 输入、输出、返回值和副作用符合调用方契约；公共函数签名变化已同步全部调用方。
- [ ] 已检查 `null`、`undefined`、空字符串、空数组、零值、负数、重复值和异常类型。
- [ ] 已检查首尾、上下限、越界、排序稳定性、去重、浮点精度和时区/跨日边界。
- [ ] 条件分支无反转、遗漏、不可达代码和错误的提前返回。
- [ ] 默认行为对旧用户安全，新开关的缺省值不会意外改变既有行为。
- [ ] 错误不会被静默吞掉；用户需要知道失败时有可见、可理解的反馈。
- [ ] 操作可重入或已防重：重复点击、重复事件、重试不会重复写入或破坏状态。

### 5.2 异步、生命周期与资源

- [ ] Promise 被正确 `await` 或显式处理，无未处理拒绝和错误时序假设。
- [ ] 外部异步调用有失败路径；可能悬挂的截图、OCR、翻译、网络或系统调用有超时处理。
- [ ] 并发请求不会用旧结果覆盖新状态；组件销毁后不会继续更新失效状态。
- [ ] 取消、失败、空结果和提前返回都能恢复 UI、窗口、加载态和占用资源。
- [ ] 定时器、监听器、订阅、Worker、文件句柄和临时 URL 有配对清理。
- [ ] 事件监听不会重复注册，销毁顺序和多次初始化均安全。

### 5.3 状态与持久化数据

- [ ] 状态更新不存在 stale state、意外共享引用、非预期响应式丢失或跨实例污染。
- [ ] 内存状态与数据库状态的一致性明确，失败时不会只更新一半。
- [ ] 读写字段、类型、默认值和版本标记前后兼容；旧文档有合理降级或迁移。
- [ ] 迁移幂等，可重复执行；失败不会破坏原始数据，回滚路径明确。
- [ ] 删除、覆盖、批量更新和同步合并有边界保护，不会造成不可恢复的数据损失。
- [ ] 缓存键、失效条件和版本号正确，升级后不会继续读取过期数据。
- [ ] 用户可导出的数据与恢复结果一致，恢复过程不会意外泄露或丢失字段。

### 5.4 安全与隐私

- [ ] 源码、测试、日志、错误上报、截图和文档中没有真实 appkey、secret、token 或个人数据。
- [ ] 用户输入、外部 API 返回和 OCR/翻译结果均视为不可信数据，已检查 HTML 注入、URL 和文件路径使用。
- [ ] 密钥不会进入不该包含密钥的同步负载、配置导出、备份或前端日志。
- [ ] Electron 主进程、preload 和 IPC 的输入有边界校验，不扩大不必要的 Node/系统能力。
- [ ] 权限和合规收窄只作用于目标平台，不会因条件判断错误影响其他端或绕过商店要求。
- [ ] 第三方依赖升级已核对来源、版本、锁文件和实际影响，没有顺便引入无关依赖。

### 5.5 UI、交互与可访问性

- [ ] 加载、空态、错误、成功、禁用和部分失败状态均有合理表现。
- [ ] 快速点击、重复提交、弹窗重复打开、Escape、返回和路由切换不会破坏状态。
- [ ] 长文本、多语言、极大/极小窗口和滚动区域不溢出、不遮挡主要操作。
- [ ] 键盘焦点、按钮可用性、可点击区域和基础可访问性没有倒退。
- [ ] 错误提示不只出现在用户不可见的隐藏窗口或控制台中。
- [ ] 样式使用项目主题变量；暗黑模式、护眼绿主色和背景图下可读性未受影响。

### 5.6 性能与稳定性

- [ ] 大列表、大文档和批量操作不会引入不必要的全量复制、重复计算或频繁同步 I/O。
- [ ] watcher、事件和定时任务不会因依赖过宽形成循环或高频执行。
- [ ] 缓存有容量/生命周期和失效策略，不以永久增长换取速度。
- [ ] 重资源按需加载的方式符合目标平台限制，首屏和主线程没有明显新增阻塞。
- [ ] 性能优化有真实场景依据，没有用复杂度替换可测量的问题。

### 5.7 可维护性与变更卫生

- [ ] 新代码和本次修改的逻辑符合《代码规范》，没有借功能变更重排历史文件。
- [ ] 代码复用现有工具与模式，没有重复实现、单实现的无意义抽象或未来才使用的配置。
- [ ] 修改范围聚焦，未混入无关格式化、重构、依赖或文件移动。
- [ ] 命名、类型和注释反映当前行为；过时注释和文档已同步。
- [ ] 没有以 `any`、非空断言、忽略错误或放宽类型来掩盖真实问题。
- [ ] 没有无说明的注释代码、死分支、调试输出、临时兜底和硬编码环境路径。
- [ ] 新增持久化数据沿用模块化 `*-db.ts` 等既有模式，跨平台能力走 adapter。

## 6. 本项目专项检查清单

### 6.1 桌面端共享代码与平台适配

- [ ] 业务代码没有直接调用 `utools.*`、`wx.*` 或 IndexedDB；跨端能力通过 `src/adapters/`。
- [ ] 非 uTools 环境在使用同步 `getDbAdapter()` 前已 `await getDbAdapterAsync()`。
- [ ] `__PLATFORM__`、`__STORE_BUILD__` 和条件分支覆盖正确，不会把某端行为泄漏到其他端。
- [ ] 共享 `src/` 修改已评估 uTools、Web、Electron，不只验证开发时正在使用的一端。
- [ ] 路由、Pinia 持久化、构建宏和 Vitest 别名变化已检查桌面与移动测试解析差异。

### 6.2 uTools 与 Electron 链路

- [ ] 每个 `hideMainWindow` 后，成功、失败、取消、空结果和提前返回均通过 `try/finally` 等方式配对恢复。
- [ ] 截图、OCR、翻译等外部异步操作均有超时和可见错误，不存在悬挂。
- [ ] 空识别、空选词有用户可见提示，不静默返回。
- [ ] 新增 action 无 fall-through、误分派或默认入口误判，`addWordActions` 等排除清单同步。
- [ ] 不盲信 `action.payload`；主输入框、超级面板和系统选中文本的来源与语义区分正确。
- [ ] 专注模式的主窗口通信通道、数据库兜底和窗口关闭行为保持兼容。
- [ ] Electron 全局热键、子窗口和 preload 变更已检查权限边界及成功/失败清理。

### 6.3 复习算法与业务数据

- [ ] 复习等级、升降级、间隔数组索引、`isReview`、`remember` 的边界符合既有算法约定。
- [ ] 单词主列表与听写等模块使用同一套复习语义，没有各自漂移。
- [ ] 跨日、时区、连续打卡、到期判断和批量修改使用一致时间语义。
- [ ] 词库切换、语言切换、默认词库和旧 `words-list` 数据兼容未受破坏。
- [ ] 同步冲突、删除标记、重复数据和离线修改不会造成复活、丢失或重复写入。

### 6.4 移动端与小程序

- [ ] `mobile/src` 的修改已检查 Pinia 2.x 与桌面端 Pinia 3.x 的差异，不能直接照搬桌面用法。
- [ ] 微信小程序没有运行时动态 `import()`；数据与重模块使用静态 import。
- [ ] 分包之间没有禁止的模块互引，静态资源路径和生成后的 chunk 落点正确。
- [ ] 新页面根节点使用 `themeClass`，颜色使用 `--sr-*` 变量；原生导航栏/tabBar 配色未遗漏。
- [ ] 小程序 CSS 的高度、滚动、`box-sizing` 和固定 `vh` 约束未被破坏。
- [ ] 拍照、相册、OCR、分享 canvas、音频和地图等原生能力已检查权限、取消、失败和真机差异。
- [ ] 低优先平台至少未被共享代码演进破坏，构建结果与声明一致。

### 6.5 生成数据、脚本与发布产物

- [ ] 修改源 JSON/Markdown/公式/几何数据后运行了对应转换或渲染脚本，未手改生成文件。
- [ ] 知识包内容变化同步更新版本号及要求的镜像/映射，缓存能正确失效。
- [ ] 诗词内容变化后重新生成拼音，英译和来源字段遵守项目约定。
- [ ] 构建脚本、SEO 页面、商店剥离和 NOTICE 处理与源数据保持一致。
- [ ] `dist/`、`dist-electron/`、`release/` 未被手工修改；验证从规定命令重新生成。
- [ ] 测试运行新增的日志、截图、报告和临时文件已按仓库规则处理，没有混入提交。

## 7. 测试与验证结果审查

- [ ] bug 修复有能锁定原始问题的回归测试，非平凡新逻辑有正常、边界和失败路径测试。
- [ ] 回归测试能区分修复前后；若未在旧代码上确认会失败，记录原因和其他证据。
- [ ] 测试验证可观察行为，不只是调用即成功、快照变大或 mock 自身返回自身。
- [ ] mock 没有绕过本次修改的核心逻辑；适配器、旧数据和跨端条件有适当覆盖。
- [ ] 修改 `App.vue` 入口、`pic-translate.ts` 或 plugin features 时同步更新并运行 `src/app-enter.test.ts`。
- [ ] UI/路由改动有受影响真实构建产物的黑盒 E2E，不只验证源码环境。
- [ ] 最终全量命令、构建和场景验证均针对最新代码，结果没有从旧运行复制。
- [ ] flaky 测试、跳过测试和既有失败已明确列出，没有通过重跑或改断言隐藏。
- [ ] 改动涉及缓存、跨天时间、异步落盘、分片、同步密钥、手势或过期响应时，已对照《代码规范》第 14 节完成同类缺陷防复发检查。
- [ ] 审查结论区分静态证据、运行时复现和产品口径，未把待复验假设写成“全部成立、无误报”。

## 8. 全库审计规程

### 8.1 触发与范围

以下任一情况触发全库审计：重大版本发布、数据/同步/安全架构重大调整、同类严重缺陷重复出现。除此之外，每季度安排一轮，可分模块完成，也可与重大版本审计合并。

默认覆盖：

- `src/`：页面、stores、adapters、utils、router、入口、配置和测试。
- `mobile/src/`：主包页面、分包、stores、adapters、utils 和测试。
- `electron/`、`public/preload/`、`public/focus.html`、`public/plugin.json`。
- `vite.config*.ts`、`vitest.config.ts`、TypeScript 配置、electron-builder 配置和 CI。
- `scripts/` 中构建、发布、数据生成、同步和测试脚本。
- 第一方数据生成源文件及其生成一致性。

`node_modules/`、构建产物、覆盖率产物和第三方依赖不作逐行人工审查，但必须检查依赖风险、调用边界、构建结果和生成一致性。无法覆盖的目录或文件必须列入“未覆盖范围”。

### 8.2 执行顺序

1. **固定版本**：记录 commit、工作区状态、Node/npm 环境和审计人。
2. **建立清单**：列出上述目录及模块，按数据/安全/入口/共享逻辑优先排序。
3. **运行全量门禁**：执行 CI 同等测试、类型检查、四端构建和三端 E2E；失败先登记，不得跳过。
4. **逐模块审查**：沿入口、调用链、状态、存储、外部服务和 UI 阅读，执行第 5～7 节适用项。
5. **跨模块追踪**：重点检查 adapter 实现一致性、同步与备份闭环、密钥流向、复习算法共用逻辑和生成数据链路。
6. **真实场景验证**：按风险执行 uTools/Electron/Web/微信小程序场景；平台模拟无法覆盖的项目必须实机或明确未验证。
7. **登记并分级**：所有发现使用统一格式，阻断/严重问题立即进入修复流程。
8. **修复与复审**：回归测试证明修复有效，重新执行受影响门禁，并检查同类问题是否存在于其他调用方。
9. **形成结论**：只有清单全部有结果、未覆盖项明确、门禁通过且没有未接受的阻断/严重问题，才能给出全库审计通过结论。

### 8.3 审计覆盖记录

每轮审计至少保留以下信息，可放在 PR、issue 或当次发布记录中：

```text
审计版本/日期：
审计人及轮次：
覆盖目录与模块：
明确排除项：
未覆盖项及原因：
执行的命令与结果：
实机/场景验证：
发现清单及严重度：
修复提交与回归证据：
剩余风险与后续期限：
最终结论：通过 / 修改后复审 / 不通过
```

## 9. 审查发现与变更审查记录

### 9.1 问题格式

```text
[严重度] 简短标题
位置：path/to/file.ts:行号
证据/复现：最小输入、操作步骤或失败测试
实际结果：
预期结果：
影响：用户、数据、平台、安全或发布影响
建议：优先修复根因，说明需要同步检查的调用方
验证：修复后应通过的测试或场景
```

禁止只写“这里可能有问题”。无法复现但必须保留的疑点应标为“待验证假设”，并写明还需要什么证据。

### 9.2 变更审查记录模板

```text
审查对象（commit/diff）：
目标与验收标准：
风险等级：低 / 中 / 高
受影响平台与数据：
已阅读的上下文、调用方和关键模块：
审查轮次：第一轮 / 独立复审

自动检查：
- 命令：结果（通过/失败/未运行及原因）

人工场景：
- 场景：结果与证据

审查发现：
- 编号、严重度、处理状态和回归证据

未验证项与剩余风险：
最终结论：通过 / 修改后复审 / 不通过
```

“通过”的最低条件是：没有未接受的阻断或严重问题，必跑门禁全部通过，适用检查项均已完成，未验证项已经明确记录且不影响本次结论。
