# 同步「删除复活」问题与墓碑（tombstone）方案设计

日期：2026-09-16
状态：**仅设计，暂不实施**（用户确认后再动手）

## 问题

当前多端同步（服务器同步码 / 文件 / 坚果云 WebDAV）的还原语义是**按 id 合并**：
本地已有的 id 保留本地版本，远端独有的 id 追加进来。

这导致「删除复活」：设备 A 删除了某条目 → 设备 B 还留着 → B 下次推送 → A 拉取后被删的条目又回来了。

## 候选方案

### 方案一：墓碑表（推荐）

每个同步模块额外维护一份删除记录：

```
{ module: 'textMemory', deletedIds: { [id]: 删除时间戳 }, ... }
```

- 删除条目时同步写入墓碑（本地持久化，随同步包一起传输）。
- restore 合并时跳过墓碑里的 id（墓碑时间晚于条目更新时间才跳过）。
- 墓碑保留一个窗口期（建议 30 天）后清理，避免无限膨胀。
- 优点：条目本身不动，老版本数据兼容；缺点：每个模块都要加墓碑读写，改动面大。

### 方案二：软删除标记（变体，改动稍小）

条目上加 `deleted: true` + `utime`（最后修改时间）：

- 删除改为打标记；列表查询全部过滤 `deleted`。
- 合并时按 `utime` 仲裁（最后写入获胜）。
- 定期物理清理过期软删条目。
- 缺点：每个模块的查询/统计都要加过滤条件，容易漏；条目体积常驻。

## 影响模块

词库（words）、文本记忆（textMemory）、数字记忆（numberMemory）、
快捷键记忆、字母映射、知识库进度、音标进度、打卡、记忆宫殿、句子库（sentences）。

## 工作量评估

中等。每个模块：删除入口埋点 + restore 合并逻辑 + 清理逻辑 + 测试。
建议先做高频模块（词库、文本记忆、句子库），低频模块随后。

## 决策

暂缓。当前缓解措施：同步语义已从「覆盖」改为「按 id 合并」（2026-09-16），
误删后可在另一台设备找回；复活问题仅在「删除后另一设备又推送旧数据」时出现。
