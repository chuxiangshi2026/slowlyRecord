#### P0-5 统计域名外部复核

当前代码端点为：


历史记录显示 11 月 26 日端点已通过；11 月 27 日分析期间，当前 WSL 请求出现 `Couldn't connect to server`、HTTP 000。该失败尚未排除 sandbox 或代理影响，不构成“线上服务故障”的确认依据。

按以下顺序复核：

1. 记录测试时间、网络环境和代理是否启用，只记布尔状态，不输出代理认证地址。
2. 先尝试本地 DNS 和 HTTPS；受 sandbox 限制时按规定申请执行权限。
3. 在已获授权的 Windows 宿主或其他外网复测；没有控制权限则列外部条件，不绕过审批。
4. 对比域名解析失败、连接失败、证书失败、HTTP 应用错误，分别归因。
5. 本地网络失败但其他环境成功，记录环境差异；多环境都失败才升级调查，仍需保存具体响应。

以下命令是有限的诊断模板，每条都添加连接与总超时；保存脱敏响应及 HTTP 状态，不能只看 curl 进程退出码：

```bash
curl -4 --connect-timeout 10 --max-time 20 -i -X OPTIONS https://stats.slowrecap.cn/collect
curl -4 --connect-timeout 10 --max-time 20 -i -X POST https://stats.slowrecap.cn/collect \
  -H 'Content-Type: application/json' \
  -d '{"name":"test.check","url":"/","platform":"web","appVersion":"test","installId":"local-test","ts":0}'
curl -4 --connect-timeout 10 --max-time 20 -i https://stats.slowrecap.cn/collect
curl -4 --connect-timeout 10 --max-time 20 -i -X POST https://stats.slowrecap.cn/collect \
  -H 'Content-Type: application/json' \
  -d '{'
```

非法事件名用 `TEST.CHECK`、超大请求用合成 40 KiB JSON，各发送一次即可；不得压测生产接口、触发持续限流或大批量写入统计。需要测试文件时以本地临时文件和 `--data-binary @文件` 传入，不把真实配置当请求样本。

预期：

- DNS 可解析；
- HTTPS 证书有效；
- `OPTIONS` 返回 204；
- 合法 `POST` 返回 200；
- `GET` 返回 405；
- 非法 JSON 返回 400；
- 超大请求返回 413；
- 非法事件名被拒绝；
- 响应头和日志不暴露凭证、用户原文或完整请求体。

合法测试事件只能使用 `test.check`、`local-test` 等标记；非法输入用于验证拒绝分支。记录事件时间范围，后续分析过滤测试事件，不擅自删除生产日志。

额外检查：

- 证书到期日：旧记录为 2027-02-24，需以当前握手证书复核；
- 是否设置强制 HTTPS；
- DNS CNAME、云函数自定义域名和回源路径是否仍一致；
- 旧统计函数地址不出现在商店产物中；
- `Origin: null`、正式 Web Origin 和无 Origin 请求的行为；
- `Access-Control-Allow-Origin: *` 是否仍是必要策略，能否在保留 uTools 兼容性的前提下收紧。

CORS、强制 HTTPS、WAF 和限流均先记录现状与建议，不在验收中直接改云配置。CORS 策略不作为认证或反滥用能力的替代；未发现实际问题前，不把通配符本身登记成发布阻断。

云端函数部署版本、网关访问日志、日志留存期限与权限若缺乏后台读权限，应标为未核实。代码中声明“不记录 IP”不能证明网关没有访问日志。

## 8. 停止、重试和升级规则

- 同一网络或工具失败，最多进行一次有明确理由的重试。
- 失败日志必须保留，不能用成功重跑覆盖首次失败。
- 没有手机、扫码、音频设备或 uTools 控制通道时，标记 `BLOCKED`，继续执行其他任务。
- 发现数据损坏、密钥泄露、核心功能崩溃或发布构建失败时，标记 Blocker/Major，停止提审建议并保留现场。
- 不因为自动化全绿而跳过真实场景。
- 不因为真实场景受阻而把未验证项写成通过。
- 不擅自扩大修改范围；发现与本计划无关的问题单独记录。

运行中的网络命令设置超时；长任务使用可轮询会话，持续给用户简短进度。阶段受阻不反复询问同一条件，完成其余独立任务后集中列出。若所有剩余项都依赖外部条件，提交完整报告并结束该批执行，不把受阻项从验收表中删除。

需要修复时：先说明复现、根因、影响和最小修改方案；用户明确授权后补能锁定原始失败的回归测试，再重跑受影响门禁。每次改代码都更新基线和证据关联，不能沿用修复前的通过结论。

## 9. 提交与发布判断

### 9.1 按平台分别给结论

| 目标 | 最低交付条件 | 尚有缺口时的表述 |
| --- | --- | --- |
| 微信小程序 | P0-1、完整 MP 矩阵有结果；MP01–MP04 数据与恢复链有证据；相机、发音、手势、后台切换等设备依赖项补真机；受影响门禁/构建和 CI 通过 | “代码与构建通过，真机/数据场景待补”，不能把模拟器整体视为真机通过 |
| Web | 最终构建、E2E、内容页与入口检查、受影响用户链路、线上依赖和 CI 有结果 | 未验证离线冷启动、旧缓存更新等需逐项说明 |
| Electron | Web 共享部分门禁之外，还需原生文件导入/导出、取消、失败和窗口复开证据 | “渲染层通过，原生能力未验收” |
| uTools 商店 | P0-1、P0-3、P0-5，商店闸门/静态扫描/E2E、权限文案、最终宿主版本和 CI 均有证据 | “代码/产物部分完成，暂不建议提审” |

未完成 MP03 故障恢复或 MP04 学习状态保护时，不因修复已提交就判定数据风险关闭。MP05 等其余矩阵项也不能省略；延期需由负责人明确评估影响，不能由代理擅自接受关键未验证风险。

Android / iOS / 抖音不成为本轮专项实机发布目标。共享代码改变时检查其基本构建兼容性，不挤占微信与桌面/Web 的收尾顺序。

### 9.2 共同门禁

- 没有未接受的 Blocker/Major。
- 最终源码、构建产物和证据身份一致；相关真实场景完成。
- 商店包只使用规定构建，统计域名迁移和脱敏有证据。
- CI 的最终 `quality` 和 `builds` 按项目发布流程通过；未查询到不写通过。
- 剩余 Minor、性能观察和未验证项有影响说明、负责人决定和后续工作。
- 报告交付、建议提审、实际上传/部署/发布是不同动作；本计划只交付建议。

全批可写“执行完成，部分验收受阻”，前提是全部事项都有状态、证据或明确外部条件。这不等于“全平台验收通过”。不能用 Electron 原生验收受阻去阻断一个完全独立的小程序结论，也不能用小程序通过替代 uTools 宿主验收。
