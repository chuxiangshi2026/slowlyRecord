# 项目代码质量审查

## 目标

依据 slowlyRecord 的现行规范执行可重复的代码审查，发现正确性、数据兼容、安全、跨端、性能和测试问题。区分代码证据、复现结果和待验证假设，不输出无依据的“可能有问题”，不把 AI 审查当成质量保证。

## 读取项目标准

先读取以下文件，并保持详细规则只在源文档维护：

- `../../../AGENTS.md`：项目架构、平台约束、命令与提交要求。
- `../../../private-docs/docs/quality-control-process.md`：变更分级、质量门禁和完成定义。
- `../../../private-docs/docs/code-review-standard.md`：审查步骤、问题定级、检查清单和全库审计规程。
- `../../../private-docs/docs/coding-standard.md`：编码、Vue/TypeScript、异步、数据、样式和测试规范。

变更审查至少读取质量流程第 3～5 节、审查标准第 2～7 节及代码规范第 13 节。发布检查额外读取 `../../../private-docs/docs/blackbox-e2e-testing.md`。全库审计读取三份标准的完整内容。

## 选择审查模式

- 用户要求“审查代码”“检查改动”“看看有没有 bug”“提交前自查”时，执行**变更审查**。
- 用户要求“复审”“高风险检查”或改动涉及数据、同步、备份、密钥、共享 adapter/store/util、复习算法、窗口生命周期、构建配置时，执行**高风险变更审查**，增加第二轮反例检查。
- 用户要求“发版前检查”“发布质量检查”时，执行**发布检查**，验证最终提交、CI、构建产物、E2E 和受影响平台实机项目。
- 用户要求“全量审查”“全库审计”时，执行**全库审计**，逐模块记录覆盖与未覆盖范围；只检查部分模块时称为专项审查或抽查。
- 用户指定文件、目录、提交或平台时，缩小执行范围，但明确剩余范围，不擅自把局部结果扩大成全项目结论。

## 固定对象与保护现场

1. 运行 `git status --short`、`git diff --stat`、`git diff`、`git diff --cached`，记录审查对象和已有工作区改动。
2. 包含属于本次任务的未跟踪源文件，排除构建产物、依赖目录和明显的本地临时文件。
3. 不覆盖、回滚或清理用户已有改动，不在审查中夹带无关格式化。
4. 默认只读审查源码。允许运行规定测试和构建；不修改业务代码，除非用户明确要求“审查并修复”。
5. 不因工具或 AI 建议擅自安装依赖、修改配置、放宽规则或扩大任务范围。

## 执行变更审查

### 1. 映射需求与影响

- 从用户要求、提交说明和代码中还原验收标准；无法确认的部分标为假设。
- 列出受影响平台、数据版本、入口、状态、持久化、外部服务和 UI。
- 阅读改动函数或组件的完整上下文，搜索全部调用方、实现方、事件发送方与接收方。
- 对 bug 修复检查共同根因和其他具有同类缺陷的调用路径，不只检查报告入口。

### 2. 应用检查清单

按代码涉及范围使用 `code-review-standard.md` 第 5～7 节与 `coding-standard.md`，重点检查：

- 空值、边界、重复操作、错误分支和提前返回。
- Promise、并发、旧请求覆盖、超时、取消及 `try/finally` 资源恢复。
- 旧数据、迁移幂等、同步冲突、备份恢复和不可回退操作。
- 密钥、日志、用户文本、IPC、文件路径和商店版合规。
- 非 uTools 数据库异步初始化、adapter 边界和跨端条件。
- uTools 窗口隐藏恢复、payload 来源和 action 分派。
- 移动端静态 import、分包引用、主题变量、原生能力取消与失败。
- 回归测试是否真正验证行为，mock 是否绕过核心逻辑。

### 3. 核实发现

- 优先用最小输入、调用链证据或现有测试复现问题。
- 给每个确认问题标注 Blocker、Major、Minor 或 Nit，并附 `path/to/file.ts:行号`。
- 将无法复现但值得继续调查的条目单列为“待验证假设”，说明缺少的证据，不与确认缺陷混合。
- 不报告与本次改动无关的个人风格偏好；历史代码问题只有在被本次变更触及或造成实际风险时列入主发现。

### 4. 执行相应门禁

所有代码变更至少运行：

```bash
npm run test:run
npm run type-check
```

修改移动端应用或移动端测试时额外运行：

```bash
npm run type-check:mobile
npm --prefix mobile run type-check:test
```

按影响范围选择构建：

```bash
npm run build
npm run build:web
npm run build:electron
npm run build:mp-weixin
```

修改 UI、路由、抽屉或弹窗时，对相应真实构建产物运行：

```bash
node scripts/e2e/blackbox.cjs --dist dist
node scripts/e2e/blackbox.cjs --dist dist-web
node scripts/e2e/blackbox.cjs --dist dist-electron
```

修改 `src/App.vue` 入口、`src/utils/pic-translate.ts` 或 `public/plugin.json` features 时，额外运行：

```bash
npx vitest run src/app-enter.test.ts
```

商店提交使用 `npm run build:store`，不得以普通构建替代。优先执行标准命令；环境受阻时记录未运行项、原因和影响，不把跳过项写成通过。

### 5. 进行高风险第二轮复审

第一轮修复或检查完成后，从需求和失败场景重新寻找反例：

- 构造异常输入、旧版本数据、并发时序和平台不支持场景。
- 检查修复是否只处理单一调用方，是否引入新默认值或兼容性分支。
- 核对回滚和数据恢复路径。
- 对第一轮“未发现问题”的高风险模块重新检查至少一个正常路径和一个失败路径。

## 执行发布检查

1. 固定最终 commit 和工作区状态，确认审查对象与发布对象一致。
2. 检查 CI `quality` 和 `builds`，不能仅依赖本地早期结果。
3. 按质量流程执行四端构建、三端产物 E2E 和受影响平台真实场景。
4. 核对数据迁移、备份恢复、回滚、商店构建和已知问题。
5. 存在未接受的 Blocker/Major、必跑项失败或未披露的关键未验证项时，结论为不通过。
6. 不擅自发布、推送、打 tag、修改版本或上传产物。

## 执行全库审计

1. 按 `code-review-standard.md` 第 8 节建立目录与模块清单。
2. 覆盖 `src/`、`mobile/src/`、Electron/preload、构建配置、CI、相关脚本和第一方生成数据链路。
3. 按数据/安全/入口/共享逻辑优先，逐模块记录已检查文件、调用链、命令和场景。
4. 排除第三方依赖和构建产物的逐行人工审查，但检查依赖调用边界和构建结果。
5. 分多次完成时保留覆盖进度。未完成全部清单前，不给出“全库审计通过”结论。
6. 对确认问题检查其他模块是否存在同类根因，并保留修复后的回归证据。

## 处理修复请求

用户明确要求修复时：

- 只修复本次审查确认且属于授权范围的问题，保持最小 diff。
- 优先修复共同根因，补充能在旧代码上失败的回归测试。
- 重新执行受影响审查和规定门禁，不复用修复前的通过结果。
- 不顺手修复无关问题；将其他发现留在报告中。

## 输出报告

使用简体中文，先给结论和最重要发现，避免长篇规范复述：

```text
结论：通过 / 修改后复审 / 不通过
审查对象与模式：
范围与风险等级：

确认发现：
1. [严重度] 标题
   位置：path/to/file.ts:行号
   证据/复现：
   实际结果与影响：
   建议与回归验证：

待验证假设：
- 仅列有必要继续调查的条目及所缺证据

验证结果：
- 命令或真实场景：通过 / 失败 / 未运行及原因

未覆盖范围与剩余风险：
```

无发现问题时明确写“在本次范围内未发现确认缺陷”，同时列出检查范围和未验证项，不写“保证没有 bug”。存在失败或关键未运行项时不得给出无保留通过结论。默认把报告放在回复中，不新建报告文件，除非用户要求存档。
